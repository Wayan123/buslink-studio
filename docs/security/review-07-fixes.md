## Accepted, with reasons

1. **`style-src 'unsafe-inline'`** (app CSP and LAN CSP). `script-src 'self'` holds and there is no `unsafe-eval`, so injected markup cannot run script. The analog bar in `src/components/tile.ts` positions its band, limit ticks and marker with inline `style="left:…%;width:…%"` attributes, which would need a rewrite to CSS custom properties set from script. The risk is cosmetic (style injection), the cost is a UI refactor late in the schedule. `scripts/check-ui.mjs` keeps the stronger control: no HTML-string sinks in `src/`, so there is no injection point to begin with. Revisit when the bars are rewritten.
2. **No native confirm dialog for high-risk writes.** The control panel and the wizard exist only for simulated devices in this release, so a bypass reaches a simulator, not a drive or a heater. The confirmation is the in-app dialog with the frame, backed by arming, bounds, read-back and audit. Webview script injection is closed by the strict CSP and the no-`innerHTML` gate. A native dialog becomes necessary when any real device can be controlled; it is a precondition for that, not for this release.
3. **Android Keystore.** On Android the MQTT password is held in memory and lost on restart, which is safe (nothing is stored), but it is not the Keystore. The UI says so (`secret_persistent`). Safety rule 14 allows "in memory". Docs and the demo must not claim Keystore storage until it is wired.

## Notes and limits

- **M1.** The role is an interlock, not authentication: see `roles.md`. The webview can still call `commissioner_unlock`; what changed is that the claim is no longer in the arm request, the raise is a separate audited step, and it ends with the arm.
- **M2.** The marker is `CommandTarget.session_simulator`, set only by `Session::command_access` from a link created by `Session::connect(.., simulated = true)`, which accepts only in-process simulator links. A user-entered TCP link, including `127.0.0.1`, is monitor-only; the control picker lists such a device with the reason. `host_of` was left as is: accepting loopback host names is fine once they confer no control rights. Not tested end to end: a manual loopback link in the running app (needs a Modbus TCP server on the PC; the unit test covers the rule).
- **L1.** The shared URL still contains `?t=` (it is the entry link and the QR code); only `GET /` accepts it, and it answers 303 to `/` with the cookie.
- **L2.** Alarm limits are not part of profiles; they travel in the snapshot's `alarms`, unchanged. The browser profile keeps `type`, `unit`, `scale`, `decimals`, `valid_range` and `display_range` because tiles, bars and trend filters use them.
- **L3.** A new connection starts in the unauthenticated pool until one request carries a valid token. If many different LAN addresses hold idle connections at once (each up to the 4-per-address cap), new viewers still wait until the 5 s handshake and 10 s header timeouts clear them; viewers that are already connected are not affected. Availability only.
- **Release guard.** It checks the unbundled exe or library. The NSIS installer and the APK are compressed, so they are not scanned. `release:android` is not exercised here (no Android build was run), and `beforeBundleCommand` is declared in `tauri.conf.json` but a full `tauri build` was not run either. I did not verify that Tauri runs it from the repository root; the command uses `--optional` so a different path does not break a build.
- Re-running the verification scripts rewrote `docs/verification/*` (screenshots, results JSON, new export files with a new session id); the old export files show as deleted in `git status`.
